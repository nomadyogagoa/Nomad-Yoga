# PostgreSQL constraints for the initial migration

These constraints are documented for a future, approved initial migration only. No migration or database command has been run.

- `ProgramSession.capacity > 0` and `endAt > startAt`.
- `PracticeSession.durationMinutes >= 0`.
- Hostel: `RoomType.capacity > 0`, non-negative prices; `HostelBooking.checkOutDate > checkInDate`, `adults > 0`, `children >= 0`, non-negative money; `HostelBookingUnit.nights > 0`; and `RoomPriceRule.endsOn >= startsOn`, non-negative rates, and a positive supplied `minNights`.
- Hostel allocation: PostgreSQL-backed concurrency tests remain required once a development database is approved. The initial migration review should consider transaction isolation or exclusion/locking protections so a room or bed cannot receive overlapping `CONFIRMED` or `CHECKED_IN` booking units. Test two overlapping creates and two simultaneous `PENDING -> CONFIRMED` transitions against the same room and bed.
- Store: cart and order quantities must be positive; inventory quantities must be non-negative; product, variant, order, and order-item money must be non-negative. The initial PostgreSQL migration should add checks for `quantityOnHand >= 0` and `quantityReserved >= 0`.
- Cart: `userId IS NOT NULL OR sessionId IS NOT NULL`.
- Store orders: checkout uses conditional `UPDATE Inventory ... WHERE quantityOnHand >= requested` inside one transaction. PostgreSQL integration tests must verify this prevents overselling under concurrent checkout requests. Unpaid `PENDING` order cancellation restores stock exactly once by transitioning the order before incrementing inventory. Test concurrent cancellation/status updates as well as checkout. Stale unpaid orders need an explicit future expiration policy.
- Programs: `ProgramSession.capacity > 0` and `endAt > startAt`. Course booking confirmation must re-count `CONFIRMED` bookings in the same transaction; PostgreSQL integration testing should verify concurrent free bookings and payment webhooks cannot overbook a session. `PracticeSession` automatic class entries use an application-level lookup because the approved schema has no unique `(userId, programSessionId, source)` constraint.
- CMS: review unique `(pageId, sortOrder)` ordering only if the product requires strict position uniqueness. Blog and content JSON are authored data; the frontend must sanitize any rich HTML before rendering. Newsletter double opt-in and tokenized unsubscribe require a dedicated future token model.
- Payments and memberships: monetary amounts must be non-negative, `Subscription.endsAt > startsAt`, and a partial unique index should limit each user to one active subscription once statuses are finalized. Test duplicate webhook delivery using the same `(gateway, gatewayEventId)` and verify only one payment transition, booking/order confirmation, and transaction row occur. Test duplicate/refused refund provider responses and ensure a failed `Refund` insert does not produce a delivery email.
- Newsletter: the unique `(campaignId, subscriberId)` delivery record prevents duplicate preparation records. PostgreSQL integration tests must verify concurrent `prepare` and `send` calls cannot send the same subscriber twice; current synchronous batch sending is not a replacement for a durable queue/outbox.
